# Prompt 0045 — Process monthly minimum fees

Implement the monthly minimum fee calculation for a given calendar month.

## Goal

Introduce:

    MonthlyFees::Process.call(period)

`period` represents the calendar month being evaluated and follows the existing `MonthlyFee#period` convention: a `Date` representing the first day of the month.

For every merchant, determine whether the order commissions actually applied through completed disbursements during that month reached the merchant's configured `minimum_monthly_fee`.

## Monthly commission attribution

Treat a commission as belonging to the month in which its disbursement is completed, using `Disbursement#disbursed_on`.

Do not attribute commissions to a month using `MerchantOrder#ordered_on`.

This distinction is especially important for WEEKLY merchants. A weekly disbursement may contain orders placed across two calendar months. The commissions from those orders belong to the month in which that weekly disbursement is completed.

For example, if a WEEKLY merchant has a disbursement completed on February 4 containing orders placed between January 29 and February 4, the commissions from that disbursement contribute to February's monthly minimum fee evaluation.

This keeps the monthly fee calculation aligned with commissions that have actually been applied through completed disbursements rather than commissions that could potentially be generated by orders not yet disbursed.

## Source of truth for commissions

Use the persisted `MerchantOrder#fee_cents` values associated with the merchant's disbursements completed during the requested month.

Do not recalculate commissions through `Commissions::Calculator` as part of monthly fee processing.

A persisted `fee_cents` represents the historical commission actually applied when the order was disbursed. Recalculating historical commissions would be unsafe because commission rules may change over time and current rules must not be applied retroactively to already processed orders.

The monthly fee processor therefore consumes persisted commission data and does not modify merchant orders or calculate missing order commissions.

## Calculation

For each merchant:

1. Select the merchant's disbursements whose `disbursed_on` belongs to the requested calendar month.
2. Sum the persisted `fee_cents` of the merchant orders belonging to those disbursements.
3. Calculate:

       monthly_fee_cents = [
         merchant.minimum_monthly_fee_cents - commissions_cents,
         0
       ].max

All values are already represented as integer cents.

No additional monetary rounding is necessary when summing persisted commissions or subtracting them from the configured minimum.

A merchant with no commissions from completed disbursements during the period therefore receives a monthly fee equal to its configured minimum.

## Persistence

Persist one `MonthlyFee` for every merchant and evaluated period.

Persist the result even when:

    amount_cents = 0

A zero-value record means that the merchant/month was evaluated and the minimum had already been reached.

Use the existing unique merchant/period persistence guarantee so that processing the same month multiple times remains idempotent.

Reprocessing a period must produce the correct stored result without creating duplicate records.

## Period contract

The public API expects `period` to be a `Date` representing the first day of the month.

Reject values that do not respect this contract rather than silently normalizing different representations.

Examples:

    MonthlyFees::Process.call(Date.new(2026, 1, 1)) # valid
    MonthlyFees::Process.call(Date.new(2026, 1, 15)) # invalid

## Responsibilities

Keep `MonthlyFees::Process` focused on evaluating and persisting monthly minimum fees.

It should consume the historical commission values produced by disbursement processing.

It must not:

- create or process disbursements,
- calculate or persist missing order commissions,
- modify merchant orders.

There is no need to introduce additional processing classes unless the implementation develops a concrete responsibility that justifies them. Prefer the simplest clear implementation for the current requirement.

## Tests

Add focused specs covering at least:

- a merchant whose commissions from the period are below the configured minimum stores the remaining difference,
- a merchant whose commissions exactly reach the minimum stores zero,
- a merchant whose commissions exceed the minimum stores zero,
- a merchant with no commissions during the period stores its full configured minimum,
- only commissions from disbursements whose `disbursed_on` belongs to the requested month contribute to the calculation,
- an order's `ordered_on` does not determine the monthly attribution of its commission,
- a WEEKLY disbursement crossing a calendar-month boundary contributes all of its persisted order commissions to the month in which the disbursement is completed,
- persisted `fee_cents` values are used as-is and are not recalculated,
- merchant orders and their persisted commissions are not modified by monthly fee processing,
- a zero-value `MonthlyFee` is persisted,
- reprocessing the same merchant and period is idempotent,
- an invalid period is rejected.

Keep these specs focused on observable monthly fee behavior. Do not duplicate commission rule tests already covered by `Commissions::Calculator`.

## Documentation

Update the README with the relevant interpretation and design decisions because the challenge does not explicitly define how monthly minimum fees interact with disbursement periods that cross calendar-month boundaries.

Document that:

- monthly commission attribution is based on `Disbursement#disbursed_on`, not `MerchantOrder#ordered_on`;
- commissions are considered part of the month in which their disbursement is completed;
- for a WEEKLY disbursement spanning two calendar months, all commissions in that disbursement belong to the month in which the disbursement is completed;
- persisted `MerchantOrder#fee_cents` values are the historical source of truth for commissions already applied;
- monthly fee processing deliberately does not recalculate commissions, because commission rules may change over time and recalculation could incorrectly apply newer rules to historical orders;
- the monthly fee processor only consumes completed disbursement data and never creates commissions or changes merchant orders;
- a `MonthlyFee` with `amount_cents = 0` is still persisted to distinguish an evaluated merchant/month from one that has not been processed.

Keep the README focused on the interpretation, invariants, and rationale rather than straightforward implementation details.
